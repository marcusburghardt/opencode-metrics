## Purpose

Define the dimensional SQLite schema, metrics catalog, and migrations used by the plugin and backfill.

## Requirements

### Requirement: Dimensional Database Schema

The metrics database SHALL use a dimensional model with separate
dimension tables (sessions, projects) and a fact table (measurements).
A metric_definitions catalog table SHALL describe every metric stored
in the database. All table creation statements SHALL use IF NOT EXISTS
to ensure idempotency.

#### Scenario: Schema supports new metrics without migration

- **GIVEN** the database schema is initialized with v1 metrics
- **WHEN** a future plugin version adds a new metric (e.g.,
  tokens_search)
- **THEN** the new metric SHALL be added as new rows in
  metric_definitions and measurements
- **AND** no ALTER TABLE or schema migration SHALL be required
- **AND** existing data SHALL remain intact and queryable

#### Scenario: Grafana SQL queries work against the schema

- **GIVEN** the database contains session metrics
- **WHEN** a user queries daily cost with:
  SELECT date(recorded_at/1000, 'unixepoch') as day,
  SUM(value) as cost FROM measurements
  WHERE metric_name = 'cost' GROUP BY day
- **THEN** the query SHALL return valid time-series data

### Requirement: Concurrent Write Safety

The metrics database SHALL operate in WAL journal mode with a
busy_timeout of 5000ms. Write operations SHALL be wrapped with
application-level retry logic (3 attempts, exponential backoff).
All writes for a single idle event SHALL be wrapped in a single
transaction.

#### Scenario: Two instances write near-simultaneously

- **GIVEN** two OpenCode instances are running with the plugin
- **WHEN** both sessions transition to idle within milliseconds of
  each other
- **THEN** both writes SHALL succeed (one queues behind the other)
- **AND** no data SHALL be lost or corrupted
- **AND** each session's metrics SHALL be recorded correctly

#### Scenario: Write contention exceeds busy_timeout

- **GIVEN** an OpenCode instance attempts to write metrics
- **WHEN** the database is locked beyond the 5000ms busy_timeout
- **THEN** the write SHALL be retried up to 3 times with exponential
  backoff (100ms, 200ms, 400ms)
- **AND** if all retries fail, the error SHALL be logged but the
  plugin SHALL NOT crash

### Requirement: Transaction Atomicity

All database writes for a single session idle event SHALL be wrapped
in a single transaction. If any write within the transaction fails,
the entire transaction SHALL be rolled back.

#### Scenario: Partial write failure

- **GIVEN** a session transitions to idle
- **WHEN** the project upsert succeeds but a measurement insert fails
- **THEN** the entire transaction SHALL be rolled back
- **AND** the database SHALL remain in a consistent state
- **AND** the error SHALL be logged

### Requirement: Metric Definitions Catalog

The metric_definitions table SHALL be seeded on database initialization with
the same metric names, units, and aggregation types as before. Descriptions
SHALL be updated to reflect current derivation, and the update SHALL be
applied to existing databases as well as new ones (upsert on `metric_name`,
not insert-if-absent), so upgrading users can see the limitation where they
query the catalog.

| metric_name | unit | description | aggregation |
|---|---|---|---|
| cost | usd | Total session cost in USD (own session only; excludes sub-sessions) | sum |
| tokens_input | tokens | Non-cached input tokens sent to the model | sum |
| tokens_output | tokens | Output tokens generated by the model | sum |
| tokens_reasoning | tokens | Reasoning tokens consumed by the model | sum |
| tokens_cache_read | tokens | Input tokens served from prompt cache | sum |
| tokens_cache_write | tokens | Input tokens written to prompt cache | sum |
| cache_hit_ratio | ratio | Fraction of input tokens served from cache | avg |
| duration_seconds | seconds | Wall-clock session duration in seconds | sum |
| files_changed | count | Distinct files reported in assistant session snapshots | sum |
| lines_added | count | Lines added in file changes (0 for sessions recorded on OpenCode V2) | sum |
| lines_deleted | count | Lines deleted in file changes (0 for sessions recorded on OpenCode V2) | sum |
| messages_total | count | Total conversation messages exchanged in the session | sum |
| prs_created | count | PRs created in the session | sum |
| prs_reviewed | count | PRs reviewed in the session | sum |
| issues_referenced | count | Issues referenced in the session | sum |
| permission_prompts | count | Permission prompts shown in the session | sum |
| permission_wait_seconds | seconds | Total time spent waiting for permission replies in the session | sum |
| turns_total | count | Number of assistant turns in the session | sum |
| context_tokens_max | count | Peak per-turn context tokens (input + cache read + cache write) | sum |
| context_tokens_final | count | Per-turn context tokens of the last assistant message | sum |
| generation_seconds | seconds | Total model generation time across assistant turns | sum |
| generation_output_tokens | tokens | Output tokens produced during timed generation windows | sum |
| post_generation_seconds | seconds | Time between stream completion and turn completion | sum |
| compactions | count | Compaction markers in the session message history | sum |
| child_sessions | count | Direct child sessions created by this session | sum |

#### Scenario: Metric catalog is self-describing

- **GIVEN** the database is initialized
- **WHEN** a user queries SELECT * FROM metric_definitions
- **THEN** every metric stored in the measurements table SHALL have a
  corresponding entry in metric_definitions with its unit, description, and
  recommended aggregation type

#### Scenario: Line metrics description names the V2 limitation

- **GIVEN** the database is initialized on OpenCode V2
- **WHEN** a user reads the `lines_added` description
- **THEN** it SHALL state that the value is 0 for sessions recorded on
  OpenCode V2
- **AND** users SHALL NOT have to infer that the metric is unavailable

#### Scenario: Existing database receives updated descriptions

- **GIVEN** an existing metrics.db created by an earlier plugin version whose
  catalog describes `files_changed` as "Number of files changed in the
  session"
- **WHEN** the plugin initializes the database
- **THEN** the `files_changed`, `lines_added`, and `lines_deleted`
  descriptions SHALL be updated to the current text
- **AND** metric names, units, and aggregation types SHALL be unchanged

### Requirement: Timestamp Convention

All timestamp fields in the database (started_at, ended_at,
recorded_at) SHALL store Unix epoch milliseconds as INTEGER values.

#### Scenario: Grafana time-series queries use millisecond timestamps

- **GIVEN** the database contains measurement records
- **WHEN** a user queries with `date(recorded_at/1000, 'unixepoch')`
- **THEN** the query SHALL return correct date values because
  recorded_at stores milliseconds since Unix epoch

### Requirement: Schema Versioning


The database SHALL track its schema version using SQLite's
`PRAGMA user_version`. The current schema version is 6. On each startup, the
plugin SHALL read the schema version and apply any necessary migrations for
older schema versions before proceeding with normal operation. Migrations
SHALL be idempotent: re-running them on an already-current database SHALL be a
no-op.

#### Scenario: Future schema migration

- **GIVEN** a database created with an older schema version
- **WHEN** a newer plugin version requires a higher schema version
- **THEN** the plugin SHALL detect the version mismatch on startup
- **AND** SHALL apply the necessary migrations
- **AND** SHALL update PRAGMA user_version after migration

#### Scenario: Existing database migrated to version 4

- **GIVEN** a metrics.db at schema version 3
- **WHEN** the plugin starts
- **THEN** the `cost_pricing` table SHALL be created
- **AND** the `v_adjusted_costs` view SHALL be created
- **AND** the `v_adjusted_cost_deltas` view SHALL be created
- **AND** no existing tables or views SHALL be modified
- **AND** PRAGMA user_version SHALL be set to the current version

#### Scenario: Existing database migrated to version 6

- **GIVEN** a metrics.db at schema version 5 without a parent_session_id
  column
- **WHEN** the plugin starts
- **THEN** the sessions table SHALL gain a parent_session_id column
- **AND** a secondary index idx_sessions_parent SHALL exist
- **AND** the v_sessions view SHALL expose parent_session_id
- **AND** existing rows SHALL have parent_session_id = NULL
- **AND** PRAGMA user_version SHALL be set to 6

### Requirement: Sessions Table Schema


The sessions table SHALL include the columns: session_id (TEXT PK),
project_id (TEXT), agent (TEXT), model (TEXT), classification (TEXT),
budget_tag (TEXT, nullable), parent_session_id (TEXT, nullable), title (TEXT),
started_at (INTEGER), ended_at (INTEGER), metadata (TEXT). The budget_tag
column stores the budget identifier or NULL for non-tagged sessions. The
parent_session_id column stores the SDK session's `parentID` or NULL for root
sessions, and it SHALL be exposed by the v_sessions view.

#### Scenario: Existing database migrated to version 3

- **GIVEN** a metrics.db at schema version 2
- **WHEN** the plugin starts
- **THEN** the sessions table SHALL gain a budget_tag column
- **AND** existing rows SHALL have budget_tag = NULL
- **AND** PRAGMA user_version SHALL be at least 3

#### Scenario: Existing database migrated to version 4

- **GIVEN** a metrics.db at schema version 3
- **WHEN** the plugin starts
- **THEN** the cost pricing tables and views SHALL be created
- **AND** no existing tables SHALL be dropped
- **AND** PRAGMA user_version SHALL be at least 4

#### Scenario: Session record includes budget_tag

- **GIVEN** a session has been budget-classified as "Q3-platform"
- **WHEN** the session record is upserted
- **THEN** the budget_tag column SHALL contain "Q3-platform"

#### Scenario: Session record includes parent_session_id

- **GIVEN** a sub-agent session with parentID "sess-parent-abc"
- **WHEN** the session record is upserted
- **THEN** the parent_session_id column SHALL contain "sess-parent-abc"

#### Scenario: Root session stores NULL parent_session_id

- **GIVEN** a session with no parentID
- **WHEN** the session record is upserted
- **THEN** the parent_session_id column SHALL be NULL

### Requirement: Derived Metric Formulas

The following metrics SHALL be computed from SDK session data rather
than stored directly:

- `cache_hit_ratio`: computed as
  `tokens_cache_read / (tokens_cache_read + tokens_input)`.
  When the denominator is zero, the metric SHALL be recorded as 0.
- `duration_seconds`: computed as
  `(time_updated - time_created) / 1000`.
  When either timestamp is missing or the result is negative, the
  metric SHALL be recorded as 0.

#### Scenario: Division by zero in cache_hit_ratio

- **GIVEN** a session has tokens_cache_read = 0 and tokens_input = 0
- **WHEN** the session metrics are computed
- **THEN** cache_hit_ratio SHALL be recorded as 0
- **AND** no NaN or null value SHALL be written to the database

#### Scenario: Missing timestamps in duration computation

- **GIVEN** a session has time_created but time_updated is null
- **WHEN** the session metrics are computed
- **THEN** duration_seconds SHALL be recorded as 0

### Requirement: writeMetrics() computes and stores deltas

The writeMetrics() function SHALL, for each metric, read the current
value from the measurements table, compute the delta
(new_value - previous_value), insert the delta into measurement_deltas
using INSERT OR IGNORE (if non-zero), and then perform the existing
UPSERT into measurements. The OR IGNORE clause ensures that a
primary key collision on the delta table (near-impossible sub-millisecond
idle events) degrades gracefully without aborting the cumulative write.
All operations SHALL occur within the caller's transaction scope.

#### Scenario: writeMetrics called within a transaction

- **GIVEN** a database transaction is active
- **WHEN** writeMetrics() is called with 15 metrics
- **THEN** up to 15 delta rows SHALL be inserted into
  measurement_deltas (skipping zero deltas)
- **AND** 15 rows SHALL be upserted into measurements
- **AND** all operations SHALL be part of the active transaction

### Requirement: Tool call output access


The PartInfo interface SHALL include an `output` field so that extraction
functions can access tool call outputs (e.g., PR URLs from `gh pr create`
output). The SDK adapter SHALL populate this field for tool-type parts by
joining the `type: "text"` entries of the tool's `state.content` with
newlines. When the tool call has no text content (pending, failed, or
non-text-only output), the adapter SHALL set `output` to an empty string and
SHALL NOT raise.

#### Scenario: PartInfo carries tool output

- **GIVEN** a tool part whose `state.content` contains text entries
- **WHEN** the SDK adapter maps the part to PartInfo
- **THEN** the PartInfo `output` field SHALL contain the text joined with
  newlines
- **AND** artifact extraction SHALL see a single string, as in V1

#### Scenario: Tool part without text content

- **GIVEN** a tool part whose `state.content` is empty or contains only
  non-text entries
- **WHEN** the SDK adapter maps the part to PartInfo
- **THEN** the PartInfo `output` field SHALL be an empty string
- **AND** the adapter SHALL NOT raise

### Requirement: Extraction resilience

Extraction SHALL be best-effort per command. A failure to parse
one bash tool call (malformed output, unexpected format) SHALL NOT
invalidate successfully extracted artifacts from other tool calls
in the same session. The count-equals-detail invariant holds for
the successfully extracted set.

#### Scenario: One malformed tool call does not discard other artifacts

- **GIVEN** a session with two bash tool calls
- **AND** one call's output cannot be parsed
- **WHEN** artifact extraction runs
- **THEN** artifacts from the other call SHALL still be recorded
- **AND** the count of recorded artifacts SHALL match the detailed rows

### Requirement: Cost Pricing Table Schema

The database SHALL include a `cost_pricing` table with the following
columns:
- `model_pattern` (TEXT, PRIMARY KEY) — SQL LIKE pattern
- `priority` (INTEGER, NOT NULL) — lower value = higher priority,
  derived from array index in config.yaml
- `input_price` (REAL, NOT NULL) — USD per million input tokens
- `output_price` (REAL, NOT NULL) — USD per million output tokens
- `cache_read_price` (REAL) — USD per million cache read tokens,
  NULL means zero cost
- `cache_write_price` (REAL) — USD per million cache write tokens,
  NULL means zero cost
- `reasoning_price` (REAL) — USD per million reasoning tokens,
  NULL means fall back to output_price
- `description` (TEXT) — optional human-readable label
- `updated_at` (INTEGER) — epoch milliseconds when the row was synced

The table SHALL be created in the V4 schema migration using
`CREATE TABLE IF NOT EXISTS`.

#### Scenario: Table exists after V4 migration

- **GIVEN** a database at schema version 3
- **WHEN** the plugin starts and applies the V4 migration
- **THEN** the `cost_pricing` table SHALL exist
- **AND** `PRAGMA user_version` SHALL be 4

### Requirement: Adjusted Cost View (Cumulative)

The database SHALL include a view `v_adjusted_costs` that computes
per-session adjusted costs by joining the `sessions`, `measurements`,
and `cost_pricing` tables. The view SHALL expose:

- `session_id` — from sessions
- `model` — from sessions
- `classification` — from sessions
- `budget_tag` — from sessions
- `project_id` — from sessions
- `original_cost` — the `cost` metric value from measurements
- `adjusted_cost` — recomputed from token counts and the first
  matching pricing rule, or `original_cost` when no rule matches
- `cost_difference` — `adjusted_cost - original_cost`
- `recorded_at_epoch` — recorded_at / 1000 (epoch seconds)
- `recorded_at_iso` — ISO-8601 timestamp string

Model matching SHALL use SQL LIKE against `cost_pricing.model_pattern`.
When multiple pricing rules match, the rule with the lowest `priority`
value SHALL be selected (first match wins, consistent with
classification rule semantics).

The adjusted cost formula SHALL be:
```
(tokens_input * input_price / 1000000) +
(tokens_output * output_price / 1000000) +
(tokens_cache_read * COALESCE(cache_read_price, 0) / 1000000) +
(tokens_cache_write * COALESCE(cache_write_price, 0) / 1000000) +
(tokens_reasoning * COALESCE(reasoning_price, output_price) / 1000000)
```

When `reasoning_price` is NULL, it SHALL fall back to `output_price`.
When `cache_read_price` or `cache_write_price` is NULL, they SHALL
default to 0.

#### Scenario: Pricing rule matches a session model

- **GIVEN** the `cost_pricing` table contains a rule with
  model_pattern="%claude-opus-4%", input_price=15.0,
  output_price=75.0, priority=0
- **AND** a session with model="google-vertex-anthropic/claude-opus-4-6@default"
  has measurements: cost=0.42, tokens_input=5000, tokens_output=1000,
  tokens_reasoning=0, tokens_cache_read=0, tokens_cache_write=0
- **WHEN** `v_adjusted_costs` is queried for that session
- **THEN** original_cost SHALL be 0.42
- **AND** adjusted_cost SHALL be (5000 * 15.0 / 1000000) + (1000 * 75.0 / 1000000)
  = 0.075 + 0.075 = 0.15
- **AND** cost_difference SHALL be 0.15 - 0.42 = -0.27

#### Scenario: No pricing rule matches

- **GIVEN** the `cost_pricing` table contains rules that do not match
  the session's model string
- **WHEN** `v_adjusted_costs` is queried for that session
- **THEN** adjusted_cost SHALL equal original_cost
- **AND** cost_difference SHALL be 0

#### Scenario: Multiple rules match, first wins

- **GIVEN** the `cost_pricing` table contains:
  - priority=0, model_pattern="%claude-opus-4%", input_price=15.0
  - priority=1, model_pattern="%claude%", input_price=10.0
- **AND** a session has model="claude-opus-4-6@default"
- **WHEN** `v_adjusted_costs` is queried
- **THEN** the pricing with priority=0 (input_price=15.0) SHALL be used

### Requirement: Adjusted Cost Delta View (Time-Series)

The database SHALL include a view `v_adjusted_cost_deltas` that
computes per-delta adjusted costs by joining `sessions`,
`measurement_deltas`, and `cost_pricing`. The view SHALL expose:

- `session_id` — from sessions
- `model` — from sessions
- `classification` — from sessions
- `budget_tag` — from sessions
- `project_id` — from sessions
- `original_cost_delta` — the `cost` delta from measurement_deltas
- `adjusted_cost_delta` — recomputed from token deltas and the first
  matching pricing rule, or `original_cost_delta` when no rule matches
- `cost_delta_difference` — `adjusted_cost_delta - original_cost_delta`
- `recorded_at_epoch` — recorded_at / 1000 (epoch seconds)
- `recorded_at_iso` — ISO-8601 timestamp string

The same model matching, priority, and formula semantics as
`v_adjusted_costs` SHALL apply, but operating on delta values from
`measurement_deltas` instead of cumulative values from `measurements`.

#### Scenario: Daily cost aggregation with adjusted deltas

- **GIVEN** a multi-day session has cost deltas spread across 3 days
- **AND** a matching pricing rule exists
- **WHEN** a Grafana query aggregates adjusted_cost_delta by day
- **THEN** each day's adjusted cost SHALL reflect the token deltas
  for that day multiplied by the user-defined prices

### Requirement: Convenience Views

The v_sessions convenience view SHALL expose parent_session_id
alongside all existing columns (session_id, project_id, agent,
model, classification, title, started_at_epoch, ended_at_epoch,
started_at_iso, ended_at_iso, metadata, budget_tag).

#### Scenario: Grafana query joins v_sessions with measurements

- **GIVEN** sessions with parent_session_id values stored
- **WHEN** a Grafana query joins v_sessions with v_measurements
  and filters on parent_session_id IS NOT NULL
- **THEN** the query SHALL return only sub-agent session metrics
